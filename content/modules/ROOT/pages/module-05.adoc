== Event Stream入門

Ansible Automation Platformの**Event Stream**は、一つまたは複数の`Rulebook Activation`に配信可能なイベントを収集するための便利な方法です。デフォルトのAAPルート経由で動作するため、複雑なネットワーク設定を必要とせず、サービスからWebhookイベントを簡単に受信する方法を提供します。

image::Oct-17-2024_at_09.43.05-image.png[Event Streamの図, opts="border"]

=== 目的

このラボでは、Giteaプロジェクトからイベントを受信するためのEvent Streamを作成します。プロジェクト内の特定のファイル（`alert.rules`）が変更されると、Event Streamは新しいアラートルールを自動的に適用するためにPrometheusスタックを再デプロイするRulebookをトリガーします。

[IMPORTANT]
.Ansible Automation Platform (AAP) の認証情報
====
* **ユーザー名:** `admin`
* **パスワード:** `ansible123!`
====

[IMPORTANT]
.Gitea の認証情報
====
* **ユーザー名:** `student`
* **パスワード:** `learn_ansible`
====

== タスク1: 認証情報でEvent Streamを保護する

Event Streamはトークンを使用して保護することができます。Event Streamを作成する前に、基本的な認証を提供するための認証情報を作成します。

. **認証情報ページに移動します。** `AAP`タブで、**Infrastructure** → **Credentials** に移動します。
. **新しい認証情報を作成します。** **Create credential**ボタンをクリックし、以下の値を使用します。
+
[cols="1,2,2a"]
|===
| キー | 値 | 備考

| *Name*
| `Gitea token`
|

| *Description*
| `Credential that will be used to secure an Event Stream`
|

| *Credential Type*
| `Token Event Stream`
|

| *Token*
| `ansible123!`
|

| *HTTP Header Key*
| `Authorization`
| これがデフォルトです。
|===

NOTE: 製品ドキュメントについては、こちらを参照してください: link:https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.5/html/using_automation_decisions/eda-credentials[Using automation decisions: Chapter 2. Credentials].

== タスク2: Event Streamの作成

次に、Event Stream自体を作成し、先ほど作成した認証情報をアタッチします。

. **Event Streamページに移動します。** `AAP`タブで、**Automation Decisions** → **Event Streams** に移動します。
. **新しいEvent Streamを作成します。** **Create event stream**をクリックし、以下の値を使用します。
+
[cols="1,2,2a"]
|===
| キー | 値 | 備考

| *Name*
| `Gitea project events`
|

| *Event Stream Type*
| `Token Event Stream`
|

| *Credential*
| `Gitea token`
| 先ほど作成した認証情報。

| *Forward events to rulebook activation*
| 有効
| これがデフォルトです。
|===
+
最終的なEvent Streamはこのようになります。
+
image::Nov-04-2024_at_16.28.37-image.png[最終的なEvent Streamの設定, opts="border"]

. **Event StreamのURLをコピーします。** URLの隣にある「クリップボードにコピー」ボタンをクリックします。これは次のステップで使用します。
+
image::Nov-12-2024_at_15.01.52-image.png[Event Streamのクリップボードへコピーボタン, opts="border"]

NOTE: 各Event Streamは一意のURLパスを取得するため、複数のストリームが同じデフォルトのAAPルートを使用できます。

== タスク3: Gitea Webhookの設定

Giteaプロジェクトを変更して、作成したEvent StreamのURLにイベントを送信するように設定する必要があります。

. **GiteaのWebhook設定に移動します。** `Gitea`タブで、プロジェクト**eda-alertmanager**を選択します。**Settings** → **Webhooks**をクリックし、**Add Webhook** → **Gitea**を選択します。
+
image::Nov-11-2024_at_13.39.26-image.png[Giteaで新しいWebhookを追加, opts="border"]

. **新しいWebhookのフォームに入力します。**
+
[cols="1,2,2a"]
|===
| キー | 値 | 備考

| *Target URL*
| あなたのEvent StreamのURL
| AAPからコピーしたURLを貼り付けます。

| *POST Content Type*
| `application/json`
|

| *Trigger On*
| `Push Events`
|

| *Authorization Header*
| `ansible123!`
| これは作成したトークン認証情報と一致する必要があります。

| *Active*
| ☑
| このボックスがチェックされていることを確認してください。
|===
+
image::Nov-12-2024_at_15.05.10-image.png[新しいWebhookのフォーム, opts="border"]

. **Webhookの配信をテストします。** 作成したWebhookへのリンクをクリックします。下部にある**Test Delivery**ボタンをクリックします。`AAP`タブに戻り、Event Streamを確認します。「Events received」のカウントが`1`になっているはずです。
+
image::Nov-11-2024_at_14.03.49-image.png[GiteaでWebhook配信をテスト, opts="border"]

== タスク4: Rulebook Activationの作成

次に、Event Streamで受信したイベントをリッスンするために、`Rulebook Activation`を作成します。

. **Rulebook Activationsに移動します。** `AAP`タブで、**Automation Decisions** → **Rulebook Activations**に移動します。
. **新しいRulebook Activationを作成します。**
+
[cols="1,2,2a"]
|===
| キー | 値 | 備考

| *Name*
| `Gitea project events`
|

| *Project*
| `My EDA project`
|

| *Rulebook*
| `gitea.yml`
|

| *Event streams*
| `Gitea project events`
| 作成したEvent Streamを選択します。

| *Credential*
| `AAP`
|
|===
+
アクティベーションを作成した後、出力はこのようになります。

== タスク5: GiteaからPrometheusへのワークフローをトリガーする

ファイルを変更して自動応答をトリガーすることで、この統合を実際に動かしてみましょう。

. **Prometheusのアラートルールを変更します。** `Gitea`タブで、**eda-alertmanager**プロジェクトに移動し、`prometheus/alert.rules`ファイルを開きます。鉛筆アイコンをクリックして編集します。
. **新しいアラートルールを追加します。** このファイルの内容を以下と一致するように変更し、一番下までスクロールして変更をコミットします。
+
[source,yaml]
----
groups:
- name: selinux status
  rules:
  - alert: selinux disabled
    expr: node_selinux_current_mode == 0
    for: 10s
    labels:
      severity: page
    annotations:
      summary: "selinux is disabled on {{ $labels.instance }}"
- name: DiskUsageAlerts
  rules:
    - alert: RootDiskSpaceLow
      expr: node_filesystem_avail_bytes{mountpoint="/"} < (0.2 * node_filesystem_size_bytes{mountpoint="/"})
      for: 10s
      labels:
        severity: warning
      annotations:
        summary: "Low Disk Space Alert on {{ $labels.instance }}"
        description: "Available disk space on {{ $labels.mountpoint }} is below 20%."
----
+
このプッシュイベントにより、Prometheusの設定を更新する新しいジョブテンプレートが開始されます。

. **Prometheusで新しいアラートを確認します。** ジョブテンプレートが完了したら、`Prometheus`タブに移動します。「Alerts」セクションの下に、ディスクスペース低下に関する新しいアラートが表示されるはずです。
+
image::Nov-12-2024_at_08.09.50-image.png[Prometheusの新しいディスクスペースアラート, opts="border"]

== タスク6: PrometheusからAAPへのワークフローをトリガーする

では、新しいアラートをトリガーしてみましょう。

. **RHELノードのディスクスペースをいっぱいにします。** `RHEL1`または`RHEL2`タブのどちらかから、この一連のコマンドを実行します。
+
[source,bash]
----
df -h
sudo fallocate -l 25G /bigfile
df -h
----
+
出力は、`/`にマウントされたデバイスが80%以上使用されていることを示し、これがアラートをトリガーします。
+
image::Nov-12-2024_at_08.14.30-image.png[/ボリュームのディスクスペース低下を示す画面, opts="border"]

. **自動修正を監視します。** アラートが発行されるまでに数分かかることがあります。発行されると、イベントはAAPに送信されます。応答としてジョブテンプレートが実行され、25Gのファイルを削除することでストレージの問題を解決します。
. **Rule Auditを確認します。** AAPで**Automation Decisions** → **Rule Audit**に移動します。ディスクスペースアラートの「FIRING」と「RESOLVED」の両方のイベントが表示されます。
+
image::Nov-12-2024_at_15.16.25-image.png[ディスクスペースのRule Audit画面, opts="border"]

== レビュー

あなたはEvent Streamを作成し、それを使用してGitプロジェクトからイベントを受信し、それによって監視システムを更新しました。その後、その監視システムからアラートをトリガーし、それが自動的に修正されました。
