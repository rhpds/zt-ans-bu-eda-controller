== はじめに: 自動化と可観測性

イベント駆動型Ansibleは、可観測性と自動化の間のギャップを埋める素晴らしい方法です。多くの組織では、可観測性プラットフォームを監督するチームと、自動化を編成するチームは同じではありません。イベント駆動型Ansibleを使用すると、Prometheusのような可観測性プラットフォームによって生成されたイベントを利用して、自動化されたワークフローに影響を与え、トリガーすることができます。

この例では、Prometheusを使用して2つのRHELノードを監視します。アラートがトリガーされると、AlertmanagerがイベントをAnsible Automation Platformに送信し、そこであなたのRulebook Activationが待機して対応します。

[NOTE]
====
**Prometheus**は、アプリケーションやインフラストラクチャからメトリクスを収集・分析するオープンソースの監視システムです。

**Alertmanager**は、アラートを処理するPrometheusのコンポーネントです。アラートの重複排除、グループ化、そしてEメール、PagerDuty、あるいはこのケースのようにイベント駆動型Ansibleといった正しい受信者へのルーティングを担当します。
====

== タスク: SELinuxアラートのトリガーと修正

これから、イベント駆動のワークフロー全体を体験します。Prometheusでアラートを確認し、SELinuxを無効にしてそれをトリガーし、自動化された修正を監視します。

. **Prometheusのアラートを探索します。** link:tab-2[Prometheus]タブに移動します。上部にある**Alerts**をクリックします。「selinux disabled」という名前で設定された単一のアラートが表示されます。左側にある小さな矢印をクリックして、このアラートを展開します。
+
image::image.png[PrometheusのAlertsタブ, opts="border"]
+
`expr`で始まる行は、Prometheusが評価している条件です。これは、「メトリクス`node_selinux_current_mode`が`0`（無効）と等しい場合にアラートをトリガーする」という意味です。`expr`リンクをクリックすると、Graphページに移動しますが、現在は両方のノードでSELinuxが有効になっているため、「Empty query result」と表示されます。

. **RHELノードでSELinuxを無効にします。** link:tab-3[RHEL 1]タブまたはlink:tab-4[RHEL 2]タブのどちらかに移動し、以下のコマンドを実行します。
+
[source,bash]
----
sudo getenforce
sudo setenforce 0
sudo getenforce
----
+
出力は、ステータスが "Enforcing" から "Permissive" に変更されたことを示すはずです。
+
[source,text]
----
[rhel@rhel-1 ~]$ sudo getenforce
Enforcing
[rhel@rhel-1 ~]$ sudo setenforce 0
[rhel@rhel-1 ~]$ sudo getenforce
Permissive
----

. **Prometheusでアクティブなアラートを監視します。** link:tab-2[Prometheus]タブに戻り、**Alerts**をクリックします。「selinux disabled」ルールに「(1 active)」と表示されるはずです。表示されない場合は、数秒待ってからページを更新してください。ルールを展開すると、状態は「PENDING」と表示され、その後「FIRING」に移行します。「FIRING」になると、イベントがAnsible Automation Platformに送信されます。
+
image::image.png[PrometheusでSELinuxアラートがFIRING状態, opts="border"]

. **AAPでRule Auditを監視します。** アラートが発行されるまでに1〜2分かかることがあります。発行されたら、link:tab-0[AAP]タブに移動し、**Automation Decisions** → **Rule Audit**に移動します。「SELinux was disabled (firing)」という名前の新しいエントリが見つかります。これをクリックして、*Events*タブでイベントペイロードを、*Actions*タブで実行されたジョブを表示します。
+
image::image.png[SELinuxのイベントとアクションを示すRule Audit画面, opts="border"]

. **自動修正ジョブを監視します。** `AAP`タブで、**Automation Execution** → **Jobs**に移動します。「Apply baseline」という新しいジョブが表示されます。このジョブテンプレートはイベントによってトリガーされ、SELinuxを再有効化します。ジョブをクリックして詳細を表示します。*Details*タブで、ジョブに**Limit**（制限）が適用されていることに注目してください。
+
image::image.png[ホストにLimitが適用されたジョブ詳細画面, opts="border"]
+
実行中のRulebookは、イベントペイロードからホスト名を抽出し、その値を使用してPlaybookの実行をSELinuxが無効になったノードのみに制限しました。

. **修正を確認します。** SELinuxを無効にしたRHELノードに戻り、以下のコマンドを実行します。
+
[source,bash]
----
sudo getenforce
----
+
出力は "Enforcing" になっているはずです。

. **解決済みイベントを確認します。** SELinuxが再有効化されたため、Prometheusのアラートは解消されます。このとき、Alertmanagerは「resolved」（解決済み）イベントをAAPに送信します。Rule Auditページには、「firing」イベントと「resolved」イベントの両方が表示されるようになります。
+
image::Nov-12-2024_at_14.43.58-image.png[firingとresolvedの両イベントが表示されたRule Audit画面, opts="border"]

== レビュー

レビューすると、誰かがSELinuxを無効にし、Prometheusがこれを検知してアラートを発行し、イベント駆動型Ansibleがイベントを自動的にキャッチしてPlaybookを実行し修正しました。この全プロセスは、手動での介入なしに行われました。
